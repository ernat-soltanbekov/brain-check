## Автоматическая проверка

- **80 backend-тестов**: реальные Django ORM/DRF запросы, модели, авторизация, генерация, оценка, бонусы, сохранение и сценарии отказа.
- **13 frontend-тестов**: сетевой слой, отзыв истёкшей сессии, ошибки сети, повреждённое/запрещённое хранилище, восстановление ответов, повтор с тем же ключом и тем же payload.
- `ruff check`, `ruff format --check`, `prettier --check`.
- `manage.py check` и `makemigrations --check --dry-run`.
- `manage.py check --deploy` с отдельными тестовыми production-настройками: без замечаний. Это проверка настроек, не факт публичного deployment.
- `vite build`: production bundle создаётся.
- `npm audit`: на момент проверки **0 известных уязвимостей** в установленном lockfile.

HTTP stress report: [`stress-evidence.json`](stress-evidence.json).

```text
24 повторные отправки / 8 одновременных клиентов
→ 1 сохранённая попытка
40 конкурентных чтений
→ 40 успешных ответов, 0 серверных ошибок
```

Дополнительные сценарии: повтор с изменённым payload; повторяющиеся/чужие/пропущенные question IDs; отрицательное и чрезмерное время; длинный ответ; невалидные UTF-8 и расширения файлов; устаревшая версия; изменение/удаление во время оценки; откат после ошибки записи ответов; NaN/Infinity; несогласованные verdict/score; невалидные ответы модели; oversized provider response; точное совпадение multiple choice без обращения к модели; неправильный JSON. Live-сценарий также проверяет неверный ответ с попыткой заставить модель присвоить максимальную оценку.

## Проверка настоящей модели

Отчёт: [`live-model-evidence.json`](live-model-evidence.json). Модель — **Qwen3-4B-Instruct-2507 Q4_K_M** из официальной библиотеки Ollama. Для проверки на учебном Mac использован входящий в Ollama `llama-server` в CPU-режиме, предоставляющий тот же Chat Completions HTTP API. Причина CPU-режима — GPU недоступен в песочнице. Код приложения и HTTP-контракт для этого не изменяются; сервер и модель выбираются env-переменными.

Проверены генерация, смысловое grading, analysis, recommendations и adaptive difficulty — **все с режимом live**. Модельные ответы, реальные backend-проценты, источник и созданные вопросы записаны в JSON. Тест падает при fallback. Пример живого вопроса: “What is an embedding in the context of text representation?”; эталон взят из добавленного конспекта, а неверные варианты относятся к грамматической структуре и длине текста.

На меньших Qwen2.5-моделях были обнаружены нарушения структуры и неоднозначные варианты. Это помогло проверить rejection/fallback; такие ответы не выдаются за успешную живую генерацию. Для воспроизводимого демо README рекомендует проверенную Qwen3-модель. Другие провайдеры и модели требуют своей проверки качества.

## Браузерная проверка

В desktop-браузере также подтверждены живая адаптивная генерация и реальная смысловая оценка перефразированного ответа. Выполнены: вход demo, добавление собственного конспекта, генерация по новой теме, редактирование названия, сохранение, multiple choice, переход к short answer, заполнение, reload с восстановлением, отправка, score/answer breakdown, запуск анализа. Проверены профиль/история и мобильное меню. На ширине **390 px** содержимое укладывается без горизонтальной прокрутки. Приложение использует локально включённые шрифты и не зависит от Google Fonts при запуске.

## Практические границы

- Произвольная LLM может ошибаться по смыслу. Проверяются структура, цитата, эталон и базовые признаки неоднозначности; окончательная проверка формулировок предусмотрена в редакторе.
- Mock использует совпадения слов; правильный перефразированный ответ он может недооценить. Режим явно обозначен.
- Retry защищает запись попытки, но конкурентные повторы до commit могут повторно вызвать модель. Хранилище результатов остаётся без дублей.
- Rate limits используют локальную память процесса. Для распределённого deployment нужен общий cache.
- SQLite и ограниченный HTTP stress test не являются доказательством пригодности для тысяч одновременных пользователей.
- Docker-файлы подготовлены для локального демо; Docker daemon в этой среде не работал, поэтому контейнерный запуск здесь не заявляется проверенным.
- Таймер доверяет браузерному вводу и предназначен для самостоятельной практики.
- Статус GitHub Actions следует проверять в самом GitHub после публикации. Локальные проверки не объявляются удалённым CI.
